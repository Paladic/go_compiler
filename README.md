# Грамматика Go 1.27 для LALR(1)

В parser/parser.y 614 строк, 108 правил и 344 альтернатив. В предыдущем варианте с разделением идентификаторов и выражений было 637 строк, 125 правил и 403 альтернативы. Режим LALR(1), %expect 0 и %left для [ и . сохранены. Ориентир — [спецификация Go 1.27](https://go.dev/ref/spec).

## Сборка и запуск

Нужны Flex, Bison и g++ с C++17 в PATH. Запускать из папки проекта:

```powershell
powershell -ExecutionPolicy Bypass -File ./build.ps1 -Test
./build/parser.exe ./tests/valid/if_else.go --check
powershell -ExecutionPolicy Bypass -File ./tests/Test-Parser.ps1
```

--trace включает трассировку. Коды завершения: 0 — вход распознан, 1 — ошибка исходника, 2 — ошибка запуска или чтения. AST и его проверки ещё не реализованы.

## Что изменено

- Слева от := и = используется expression_list. Для := будущий обход AST проверит, что каждый элемент — идентификатор, а не селектор, индекс, вызов или имя в скобках.
- Удалены non_identifier_* и assignment_left_*. Бинарные операторы снова описаны в expression с пятью уровнями %left.
- Объединены хвосты аргументов, списки элементов литералов и общая часть простых инструкций. Удалены обёртки package_clause, result_atomic_type и отдельные правила внешней формы switch.
- Параметры и результаты используют общие правила типов. Получатель метода сохраняет локальное имя, список имён параметров и не более одного указателя.
- chan_prefix, общий префикс [] и отдельный список результатов в скобках сохранены, чтобы не возвращать конфликты Bison.

## Что проверять после построения AST

Форма списка перед :=, одно имя в guard type switch, число получателей range/select, приём в select, допустимый префикс составного литерала, содержимое [] по контексту, вид и группировка параметров, цели переходов, fallthrough и повтор default. Отдельно нужны анализ имён и типов, адресуемость, новое имя в := и вычисление констант. Пример: user.age := 20 сейчас распознаётся; проверка AST должна его отклонить. Присваивание user.age = 20 сохраняет допустимую форму.

В [архиве конфликтов](docs/conflicts/INDEX.html) восемь отдельных папок. В каждой — candidate.y, лог Bison и конфликтующие состояния с объяснением. Эти файлы не участвуют в сборке. Два случая — направление канала и скобки результата — оставлены в грамматике; остальные показанные ограничения отложены. Для других отложенных проверок лог не приписан без отдельного эксперимента.

## Как получается исполняемый парсер

При запуске `build.ps1` выполняются три шага:

1. Bison читает `parser/parser.y` и создаёт `build/generated/parser.tab.cpp` и `parser.tab.hpp`. В `.cpp` находится алгоритм разбора с функцией `yyparse()`, в `.hpp` — объявления токенов, типов и интерфейса парсера.
2. Flex читает `lexer/lexer.l` и создаёт `build/generated/scanner.cpp` с функцией `yylex()`.
3. g++ компилирует сгенерированные файлы вместе с `main.cpp`, `Parser.cpp` и `LexerSupport.cpp` в `build/parser.exe`.

Сгенерированные `.cpp` восстанавливаются при сборке. Изменения правил вносят в `parser.y` и `lexer.l`.

| Файл | Роль |
|---|---|
| `parser/parser.y` | Написанная нами грамматика: токены, правила и приоритеты |
| `build/generated/parser.tab.cpp` | Сгенерированный Bison алгоритм разбора |
| `parser/Parser.cpp` | Написанная нами подготовка лексера и запуск разбора |
| `parser/main.cpp` | Точка входа в консольную программу |

`Parser.cpp` и `parser.tab.cpp` — разные файлы. Грамматика превращается в `parser.tab.cpp`; `Parser.cpp` только предоставляет удобный способ её запустить.

## Зачем нужен main.cpp

`main.cpp` обслуживает запуск `parser.exe`. Он получает имя файла и параметры командной строки, читает исходный текст и передаёт его в `ParseSource()`. Правила Go находятся в `parser.y`.

В файле три основные функции:

| Функция | Что делает |
|---|---|
| `ReadArguments()` | Получает аргументы командной строки. В Windows переводит их из UTF-16 в UTF-8, чтобы корректно обрабатывать пути с кириллицей |
| `Run()` | Разбирает параметры, читает файл или stdin, вызывает `ParseSource()` и сообщает результат |
| `main()` | Настраивает вывод UTF-8 в Windows, вызывает `ReadArguments()` и `Run()`, перехватывает ошибки запуска и чтения |

Например, для команды:

```powershell
.\build\parser.exe .\tests\valid\if_else.go --check
```

`main.cpp` читает файл `if_else.go`, передаёт его содержимое в `ParseSource()` и возвращает код завершения. Параметр `--check` подавляет только сообщение `Syntax OK`; сам разбор выполняется так же. `--trace` устанавливает `yydebug = 1` и включает трассировку, поддержку которой добавляет `%define parse.trace`.

Если имя файла не передано либо указано `-`, текст читается из стандартного ввода. Ошибки открытия файла и неизвестные параметры перехватываются в `main()` и приводят к коду завершения 2. Ошибка исходника приводит к коду 1.

## Зачем нужен Parser.cpp

`Parser.cpp` предоставляет одну функцию для запуска разбора из программы или тестов:

```cpp
bool ParseSource(const std::string& source,
                 const std::string& filename = "<input>");
```

Объявление находится в `Parser.h`; реализация — в `Parser.cpp`. `source` содержит уже прочитанный текст, а `filename` используется в диагностике.

Внутри выполняются следующие действия:

1. `LexerSupport::Reset(source, filename)` сохраняет текущий текст и имя файла, сбрасывает координаты, значения токенов и состояние диагностики.
2. Проверяется размер текста: функция Flex принимает длину через `int`, поэтому слишком большой ввод отклоняется.
3. `LexerSupport::ValidateSource()` проверяет допустимость исходного текста, в том числе кодировку UTF-8 и наличие запрещённого NUL.
4. Если в начале файла есть UTF-8 BOM, эти три байта пропускаются перед передачей текста сканеру.
5. `yy_scan_bytes()` создаёт входной буфер Flex из текста. `ResetLexer()` сбрасывает режим лексера и состояние вставки точек с запятой перед очередным разбором.
6. `yyparse()` запускает сгенерированный Bison парсер. Во время разбора он сам вызывает `yylex()`, когда требуется следующий токен.

Результат вычисляется строкой:

```cpp
return yyparse() == 0 && !LexerSupport::failed;
```

`true` означает, что текущая грамматика приняла текст и лексер не сообщил об ошибке. Это ещё не означает, что выполнены все проверки языка: известные ограничения перечислены ниже.

Внутренняя структура `ScannerGuard` отвечает за освобождение ресурсов. При выходе из функции её деструктор вызывает `yy_delete_buffer()` и `yylex_destroy()`: удаляет входной буфер и освобождает внутренние ресурсы сканера. Она не является нодой и не участвует в построении дерева.

Для последовательного разбора следующего файла снова вызывают `ParseSource()`. Одновременный разбор из нескольких потоков не поддерживается: Flex, Bison и LexerSupport используют общее состояние.

## Нужны ли эти C++-файлы для самой грамматики

Для проверки правил Bison и генерации его выходных файлов `main.cpp` и `Parser.cpp` не требуются. Их задача — обеспечить запуск полученного парсера.

В текущем проекте они входят в сборку программы и тестов. Простое удаление этих файлов нарушит сборку исполняемых файлов, хотя Bison по-прежнему сможет обработать `parser.y`. Какой-либо код запуска с точкой входа `main()` нужен для самостоятельной консольной программы.

Разделение запуска на два файла — решение об организации кода. Их можно объединить или упростить. Сейчас отдельная функция `ParseSource()` позволяет тестам передавать строки напрямую и многократно запускать разбор без командной строки и файлов на диске. При сборке C++-тестов `main.cpp` исключается, а точку входа предоставляет `tests/ParserStateTests.cpp`.

## Путь исходника при запуске

```text
main.cpp
  main() → ReadArguments() → Run()
                              │
                              ├─ чтение файла или stdin
                              ↓
Parser.cpp: ParseSource()
  LexerSupport::Reset() → ValidateSource()
  yy_scan_bytes() → ResetLexer()
                              ↓
parser.tab.cpp: yyparse()
  вызывает scanner.cpp: yylex() для получения токенов
  выполняет разбор по правилам parser.y
                              ↓
ParseSource() возвращает bool
  Run() возвращает код завершения
```

Успешный разбор в этой копии не создаёт никаких объектов дерева.

## Что означают значения токенов

В `%union` объявлены два способа передачи данных от лексера к парсеру:

```bison
%union {
    long long integerValue;
    const std::string* stringValue;
}
```

`%token <stringValue> DECIMAL_LITERAL` указывает, какое поле используется для данных токена. Лексер заполняет `yylval.stringValue` и возвращает код `DECIMAL_LITERAL`. Тип токена и передаваемые данные — отдельные части этой операции.

Числовые литералы сейчас сохраняют исходную запись: например, для `0xFF` передаётся текст `0xFF`. Это сохраняет основание, подчёркивания, степень и суффикс `i`, а также позволяет избежать обрезания больших целых до `long long` и округления дробей до `double`. Вычисление числовых значений выражений на этом этапе не выполняется.

`RUNE_LITERAL` передаёт декодированное целое значение через `integerValue`: например, `'A'` даёт 65, а `'\n'` — 10. Имена и строки используют `stringValue`; строковые литералы сохраняются с исходными кавычками и escape-последовательностями. Строками владеет LexerSupport, который очищает их перед следующим разбором.
